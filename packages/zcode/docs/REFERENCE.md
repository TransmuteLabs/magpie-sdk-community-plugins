Credential import uses `auth.finish` with `Input` containing a JSON object:
`site` (`zai`/`bigmodel`), `kind`
(`legacy-key`/`individual`/`team`/`start`), `userId` and `device`.
Legacy uses `key`; paid snapshots use `projectToken`; Start uses
`sessionToken`. Team additionally requires `organization`, `project` and
`product`. The initial paid/Start import requires `expiresAt` in Unix milliseconds more than
30 seconds in the future. Credentials come from `Call.Auth`, never from
an execute request's options or body. Host account ID must match the opaque
ID returned by import.

To enable ongoing paid PAT renewal, import `businessToken`,
`businessExpiresAt` in Unix milliseconds, and `location` containing
`organizationId`, `projectId`, `apiKeyId`. Team location must match its
selected organization/project. Location is part of the account identity.
PAT refresh never borrows another login or discovers/creates a new API key.
It sends one official `access_tokens` request and returns one unary
replacement to the host; no streaming acceptance event is emitted.
Expiry is the minimum of vendor absolute expiry and relative TTL measured
before the exchange. Failed or ambiguous exchanges are never retried.
For Z.ai, `oauthToken` plus `oauthExpiresAt` can renew expired business
material through the recovered `/api/auth/z/login` exchange before issuing
the PAT. Both replacements are returned as one unary result and committed
by the host together. Unknown business lifetime or a failed second stage
remains uncertain. Expired bootstrap, BigModel login renewal and
Start-session renewal require explicit sign-in; no silent refresh endpoint
is invented. The selected-account browser flow preserves account identity.

```sh
magpie plugin sdk auth start zcode zcode '{"method":"browser","input":{"site":"zai","kind":"start"}}'
magpie plugin sdk auth finish zcode zcode '{"continuation":{"id":"RETURNED_ID"}}'
```

API 1.4 usage reads echo the host's canonical revision. Reset/claim first
persist the plugin fence and receive durable acceptance, then invalidate

old-revision read cannot clear the host's dirty state; a new-revision read
cannot claim freshness while the plugin journal is unresolved. Credential
rotation is never used as cache invalidation.

## Vendor controller

Configure an absolute private `dataDir` using `plugin sdk config`.
`Start` only validates configuration; candidate installation, validation and
startup never create or migrate that directory. The first authorized
native/control call verifies the session profile and then opens storage.
The module context/disposer owns its lifetime. Do not change `dataDir`
without an explicit stopped-state migration; it is the durable namespace.

Native controls require paid credentials with `sessionToken` and
`sessionExpiresAt`. Every principal comes from this same token's
`/api/v1/oauth/profile` reply, matched to `userId`. Hashing origin/user shares
billing state across Personal, Team and Start slots. Account/task bindings,
draw cooldowns and reset state remain separate. Journal files contain no
credentials, use mode 0600, atomic rename plus fsync, and an OS lock across
processes. Corrupt/unreadable state fails closed.

The four aliases are `GLM-5.3{,-Flash}-{OffPeak,Highspeed}`. Body alias,
selected account, original conversation, raw model and vendor ticket/card
must agree. Pending admission is persisted before vendor I/O. Lost replies
remain fenced across operation IDs, restarts and PAT credential generations.
Highspeed additionally requires the business credential. Reusing a ready
execution for subsequent turns does not take another ticket/card.

Control actions are declared `module-rpc` actions:

- `execution.list`: selected account's stored references.
- `execution.settle`: one fenced Off-Peak settlement; a lost reply is not
  reposted.
- `execution.reconcile`: checks a ticket/card with the vendor. An explicit
  ticket ID is accepted only after the vendor authenticates its original
  task. Acknowledging lost inference output never marks that output known.
- `execution.abandon`: explicit uncertainty acknowledgment; old task stays
  terminal and is never retaken.
- `billing.status`, `billing.claim`: plan baseline, verified policy,
  cross-selection fence and observation after lost replies. Observed
  entitlement does not prove this claim caused it.
- `reset.status`, `reset.use`, `reset.opportunity`, `reset.ack`,
  `reset.resolve`: exact reset windows, durable keys, high-water
  reconciliation, cooldowns and explicit uncertainty acknowledgment.

All writes require a fresh `Scope.Operation` intent ID; retries of that
intent retain its ID. Credentials come only from selected `Frame.Auth`.
An in-flight ticket poll cannot overwrite abandonment, reconciliation or newer
execution progress. Its response applies only to the same still-queued ticket.
`operation.status` returns stored execution outcomes. API 1.4
`operation.cancel` uses a fresh Scope.Operation write intent and the
original operationId or reference as its target. It returns that target,
keeps the original inference journal intact and uses the same durable
Off-Peak settlement fence across callers/processes. The declared
`execution.settle` action remains available. Highspeed cancellation without
an authenticated recovered vendor exchange is explicitly unsupported.

Verification-required claims are refused before a financial POST. Reset
`used:true` alone is insufficient: newer history must confirm acceptance.
An unacknowledged lost reset reply remains unresolved even if history
advances. No scheduler automatically requests gifts, resets or cards.

The archived SQLite journal, live accounts, app state and sessions are not
automatically migrated. Before production activation, existing unresolved
vendor state needs an explicit reviewed import. Fixtures and local module
installation do not prove live entitlements or complete ZCode parity.

## Headless owner tools

Nine real ToolProvider declarations use `Exposure: local-owner`:

- `zcode_account_status`: sanitized saved identity/expiry status, no tokens.
- `zcode_usage`: informational quota observation with no revision acknowledgment.
- `zcode_mcp_usage`: official MCP aggregate, always Aside/informational.
- `zcode_image_search`: fixed official `search_image` execution with `query`.
- `zcode_execution_list`: controller references with ticket/card values removed.
- `zcode_billing_status`, `zcode_reset_status`: read-only vendor state.
- `zcode_history_inspect`, `zcode_history_convert`: explicit supplied bytes only.

For direct local management, use the SDK account scope:

```sh
magpie plugin sdk call zcode tool.call '{"id":"zcode_mcp_usage","arguments":{}}' --scope '{"provider":"zcode","account":"ACCOUNT_ID","operation":"UNIQUE_CALL_ID"}'
```

The CLI resolves the saved current generation and the host supplies
Frame.Auth. Through the existing gateway MCP bridge, `_magpie` is an
optional schema property consumed by the host. A direct module call that
still contains `_magpie`, replacement credentials, headers or arbitrary
scope arguments is rejected.

The official MCP read uses a verified selected ZCode profile, the session
JWT and the paid business/MaaS JWT; Personal/Team target is explicit.
It never substitutes a PAT/API key, refreshes credentials or downgrades to
free service. Missing paid material returns an explicit error.
Reset/claim/settlement remain their separate declared write actions with
existing durable fences.

fresh vendor data but still cannot clear host dirty state. The actual

This is exercised with separate native-host CLI calls.

`zcode_image_search` maps only to the recovered

## Offline history API

The pure `history` package exports `Read(format, body)` and
`Convert(from, to, body)`. Supported source formats are `zcode-native-jsonl`
and `zcode-legacy-session`. `Document.Summary`, `Records` and `Source` return
owned copies. Native records retain opaque blocks and signatures; legacy
snapshots retain tool details, checkpoints, file changes and body references.
External body/file references are reported and are never fetched.

Conversion to `zcode-history-bundle-v1` stores the original source bytes,
format and checked SHA-256. Restoring that original format preserves exact
bytes, including whitespace and large integers. Corrupt/recursive/unknown
bundle schemas and unsupported cross-agent targets fail explicitly.
The bundle does not authorize a live execution or make missing external
bodies complete.

The registered manual adapter is `zcode-history`. It accepts one
SessionRequest document, explicit source/target formats and
`options: {"outputPath":"relative-target"}`. Native/legacy → bundle and
bundle → its original format are supported. It rejects source overwrite,
unsafe paths, multiple/mixed inputs, unknown options and unsupported
cross-agent conversion. Its result ID is content-derived rather than an
imported task/ticket identity.

`magpie plugin sdk session` previews this file plan under an explicit
`--root` and target `--path`; only `--apply --backup-dir` writes it.
The host owns snapshots, backups and rollback. The adapter performs no IO,
vendor call or live resume and advertises no automatic agent-reader route.
Actual native preview/apply/backup/restore is verified in
[SESSION-EVIDENCE.md](history/SESSION-EVIDENCE.md).

Bounds are 8 MiB and 16,384 records for standalone sources; tool inputs
additionally limit supplied source to 1 MiB. JSON depth/duplicate-key,
UTF-8 and bundle-integrity checks apply. No source path is opened, no
installed application is inspected by this JSONL/legacy converter. SQLite
uses both the separate explicit snapshot adapter and, in the ordinary
package, the consented rooted automatic source described in
[AUTOMATIC-HISTORY.md](AUTOMATIC-HISTORY.md). Live resume remains separate.

## Settings panel and subscription sign-in

The ordinary full package includes the TS/HTML/CSS Settings panel. It discovers saved
account summaries through the host, requires explicit selection and keeps
the exact string generation. The host's fixed binding owns provider
`zcode`; no client provider, free-form scope or credentials are accepted.
The fifteen bindings expose execution summaries, plan/reset status,
explicit reset/claim/check-in and reset opportunity/history/recovery controls.
The UI-only `execution.summary` action strips
ticket/card values on the native side without changing headless
`execution.list`.

The page uses the existing sandbox/bridge and an in-page HTML dialog;
there is no sandbox-blocked browser confirm, form submission, ES-module
network load or direct backend HTTP request. Account selection is locked
while confirming or executing a write. A changed generation requires
reselection, late reads cannot overwrite a write, and uncertain actions
are never automatically repeated.

Configure the private `dataDir` separately before using native controls.
Providers → Add → Subscriptions owns sign-in and selected reauthorization. Providers also owns selected sign-out. The Settings panel retains the account selector and financial, recovery and foreground controls.

The full bundle requires `provider-saved-signin` for its `saved-signin`
method. Magpie uses this method only for local saved-account import. The
ordinary Providers form offers browser sign-in and **GLM Coding Plan API
key**. The API key method checks the selected site's quota endpoint. Use
the same method with the original site and key to sign in again to an
existing API key account. A replacement key identifies a new account.

A saved API record retains its site and key-derived identity. Preparation
checks its format. Verify its quota and routing after the transfer. A
Start-only OAuth snapshot requires
its stable UID, device, canonical site and base, matching access and session
token, and an unexpired matching JWT deadline. Completion also checks the UID
on the vendor profile and confirms an active or pending Start entitlement.
The import uses one five-minute continuation per account scope. A new explicit
import supersedes the earlier continuation, and completion consumes and clears
the pending credential snapshot before it contacts the vendor.
Preparation returns a public account summary and a ticket. Use the exact
saved account key for each record. To replace the existing subscription,
first confirm that every saved account has a supported import format. Keep
the Community plugin installed and enabled, and start with an empty SDK
account list for ZCode.

```sh
magpie plugin sdk auth import zcode zcode '<saved-account-key>'
```

Repeat import for every saved account, including paused accounts, and review
the summaries. Pass all valid tickets to `auth transfer` together. Tickets
expire after ten minutes or at the credential's earlier expiry. For a
two-account subscription:

```sh
magpie plugin sdk auth transfer zcode zcode '<first-ticket>' '<second-ticket>'
magpie plugin sdk auth owners
```

Confirm an active receipt, one ZCode subscription under the existing public
ID, the same account aliases, and ordinary Usage and routing. Keep the
receipt's `publicID` and `revision` and leave the Community sign-ins
unchanged during these checks.

If the checks fail, roll back before dispatching sign-out, reauthorization or
refresh. A refresh that the host records as `not-started` still permits
rollback. The Community plugin must still be installed and enabled.

```sh
magpie plugin sdk auth rollback '<publicID>' '<revision>'
```

After a successful transfer and checks, remove the Community plugin only
when you accept the SDK owner and no longer need rollback. ZCode's saved
accounts require `auth transfer` to preserve the existing subscription ID
and policies.

A trusted caller can still pass `auth.finish.input = {"community": <record>}`
through explicit snapshot import. The caller owns source selection, durable
publication and any subsequent retirement of the original. The package never
opens the community credential store. Paid personal and team OAuth require
browser authorization to recover their native refresh selection.

For `source:"zcode"`, the donor rereads the desktop login and adopts rotated
credentials when its display identity and, if present on both sides, vendor
UID match. The saved JWT and paid key alone do not prove that identity and
key relationship. Community 0.1.68 can decrypt the older desktop v1 format.
ZCode 3.18.2 can bind v2 credentials to the OS keyring. The SDK package has
a rooted CLI history reader and no desktop credential broker. Its saved-sign-in
method returns `reauthorization_required` before it creates a continuation or
contacts the vendor. Keep a subscription with any Desktop-follow account
under Community ownership. An ordinary browser sign-in under **Providers →
Add → Subscriptions → ZCode native** creates an independent SDK account
for the selected site and plan.

The Settings picker displays an account name from the host when present.
Selections use the exact account ID and generation. Confirmations include
the account ID.
